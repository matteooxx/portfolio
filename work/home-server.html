Case study

Home server platform

One machine, a mirrored pool and a dozen containers that someone actually depends on. The interesting part is not what it runs; it is what it was made to survive, and how each cause was established rather than guessed.

Constraint

Operated remotely, repaired rarely

Shape

A single chassis runs a ZFS mirror with scheduled snapshots and scrubs, SMART monitoring, dataset-level permissions, and containerised services behind private networking. There is no second machine to fail over to and no second site.

The operator is usually not on the home network, so almost every repair happens over a remote session with no screen, no console and nobody on site to press a button. That constraint decides most of what follows: anything that can only be fixed by standing in front of the box is a design fault, not an inconvenience.

TrueNAS SCALE, ZFS, Docker, Linux, SMART, mesh VPN

Diagnosis

A reboot that kept happening, and the counter that explained it

The machine was restarting uncleanly: about once a month for most of a year, then seven times in eighteen days. Nothing in the logs survived the event. The system log simply stopped mid-line, with no shutdown sequence after it.

  • The evidence that did survive was a SMART attribute on the boot disk that increments only when power is removed without a flush, kept in the monitoring daemon's own attribute history going back more than a year. Every unexplained restart had a matching increment, to the second, and the spinning disk logged an emergency head retract at the same moment.
  • What it was not. No kernel panic record. The hardware watchdog was inactive, with a clean boot status and nothing holding its device. No machine-check, thermal, storage or out-of-memory message on any of the days.
  • Not the house, either. A second, independent machine on the same mains stayed up continuously across two of the events, which rules out a building-wide outage and narrows the fault to something between the wall and this one chassis.
  • What was left was the component in that path nobody had questioned: the UPS. A battery that can no longer hold the load drops its output for milliseconds on a mains sag, resetting only what sits behind it, which is exactly the shape of the evidence. It was replaced, and the spontaneous events stopped.

The lesson is not about power. It is that the component assumed to be protecting the system was the one breaking it, and the only reason that was provable is that something had been recording a cheap, boring counter for a year before anyone needed it.

Recovery

Letting the battery decide, and proving the alert path

Configuration

The replacement UPS reports over USB to a monitoring daemon, with the driver taken from the scan tool rather than guessed. The stock policy shuts the machine down a fixed thirty seconds after the power goes, which would power off a healthy server over a half-minute dip. It was changed so the UPS itself signals when the battery is nearly empty, and so it cuts its own output once shutdown completes: otherwise returning mains finds a machine that never cold-starts.

The monitoring password is generated on the machine and written nowhere. Not to a file, not to a command line, not to the operations handbook.

Tested rather than assumed. The input was unplugged for a hundred and five seconds with the server live. It transferred to battery, stayed up, and the alert email was accepted one second after detection. Mains returned, and the battery was back to its float level within the hour, which also settled whether the charge reading was stuck or simply flat at the top.

What is still unproven, and says so. No event has driven the battery low enough to trigger the shutdown itself, so the handbook records the detection and alerting path as verified and the graceful shutdown as not. Writing it the other way round would cost nothing today and everything on the night it matters.

Correction

Two critical disk alerts that pointed at the wrong disk

Two CRITICAL SMART alerts sat open for a month: unreadable pending sectors, and a failed self-test. Both named a device path. On the boot that was current when they were read, that path belonged to a different physical drive than the one that had raised them. Device names are reassigned at every boot, and an alert string freezes the name from the moment it fired.

  • Re-resolved by serial, the alerts belonged to the older mirror member, which had since completed an extended self-test cleanly, hundreds of power-on hours after the failure that raised the alert.
  • Its live counters for pending, reallocated and uncorrectable sectors were all zero, and a full pool scrub three days earlier had repaired nothing and reported no errors.
  • They were dismissed on that evidence instead of re-running hours of disk I/O to re-derive what the record already said. Dismissed, not hidden: if the condition returns, the daemon raises a fresh alert.

The older drive is still treated as the suspect one. It had a real read failure, it is the senior member of the mirror, and it spent months absorbing the abrupt power loss described above.

Availability

The remote access path was a single point of failure

Remote access ran as a container on the same machine it provided access to. When that container failed, the way in failed with it, and the only thing that could have repaired it was on the other side of the door. One such failure locked the machine out for six days.

  • The stopgap was worse than it looked. The route back in briefly depended on a computer that did not belong to the operator, on the same local network. Using it meant asking another person to have their machine switched on at the exact moment something broke. It worked once, under pressure; it was never something to rely on.
  • The fix was separation. A small always-on machine now sits on the same network sharing no power supply, operating system, disk or service with the server. When the server's remote access dies, that machine is still reachable and can still reach the server locally. It also hosts monitoring, so it earns its place instead of waiting for a failure.
  • Keys stay where they belong. The credential for the server is never copied onto the second machine; the connection is tunnelled through it instead, so compromising one node does not hand over the other.

Boundary

What it deliberately is not

Scope

This is one box in one room. The memory is not ECC, the services share a single chassis, and a mirror plus snapshots protects against a disk and a mistake, not against the room. Off-site replication has been interrupted for months, which is recorded as an open gap rather than described as a backup strategy.

Hostnames, addresses, service endpoints, disk serials and the operations handbook itself stay private. What is published here is the reasoning, because the reasoning is the part that transfers.
